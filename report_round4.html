1. 报告概述

1.1 本轮背景

前三轮修复了密码安全、SQL 注入、文件上传漏洞后，系统新增了个人中心（/profile）和充值（/recharge）功能。但充值功能存在多处业务逻辑漏洞——代码在语法上没有错误，但业务规则出现严重缺陷，导致攻击者可以恶意篡改余额。

1.2 什么是业务逻辑漏洞？

业务逻辑漏洞 ≠ 代码语法错误。代码能正常运行，但业务规则设计不合理， 导致用户可以做"系统不该允许"的操作，例如：给自己充任意多的钱、把余额改成负数、不登录就改别人余额。

VULN-12：充值无金额上限 🔴 严重

位置：/recharge — POST 路由

描述：amount 参数没有上限限制，攻击者可一次充值 9999999999999 让余额变成天文数字，完全破坏系统经济平衡。

攻击场景：普通用户给自己充 9999999999999 元 → 余额变成 1 后面 13 个 0 → 账户余额失控。

VULN-13：充值可导致余额负数 🟠 高危

位置：/recharge — POST 路由

描述：amount 可为任意负数，充负值等于扣钱。如果输入比余额还大的负数，余额变成负数，代表用户可以"欠债"，这在用户管理系统中不应存在。

攻击场景：充 -99999999999999 → 余额变成巨大的负数 → 系统负债。

VULN-14：未登录也可充值（越权操作） 🟠 高危

位置：/recharge — POST 路由

描述：任何人无需登录即可直接 POST 请求 /recharge 修改任意用户的余额，只需知道 user_id。攻击者可任意篡改所有用户的余额。

攻击场景：攻击者直接 curl -X POST ... -d "user_id=admin&amount=0" 无需任何身份认证。

VULN-15：注册错误信息泄露 🟡 中危

位置：/register — POST 路由

描述：注册重复用户名时，系统直接返回 SQLite 底层错误：UNIQUE constraint failed: users.username。攻击者可以用此接口探测哪些用户名已注册。

攻击场景：尝试注册 "admin" → 报错 UNIQUE → 确认 admin 已存在 → 枚举所有用户名。

VULN-16：搜索接口未登录泄露用户数据 🟡 中危

位置：/search — GET 路由

描述：无需登录即可搜索所有用户的邮箱和手机号。输入一个简单字母即可返回大量用户信息，造成隐私泄露。

攻击场景：/search?keyword=a → 返回所有用户名中包含 a 的用户的完整资料。

3. 攻击演示

3.1 充值天文数字

📌 攻击请求
curl -X POST http://localhost:5000/recharge \
  -d "user_id=1&amount=9999999999999"

😱 攻击结果
余额从 0.0 变为 10000000000699.0（一千万亿）

3.2 充负值制造负数余额

📌 攻击请求
curl -X POST http://localhost:5000/recharge \
  -d "user_id=1&amount=-99999999999999"

😱 攻击结果
余额从正数变为 -89999999999300.0（负数）

3.3 未登录越权充值

📌 攻击请求
# 无需任何 Cookie/Session
curl -X POST http://localhost:5000/recharge \
  -d "user_id=2&amount=99999"

😱 攻击结果
alice 的余额被未登录攻击者修改为 12221212.0

3.4 注册探测用户名

📌 攻击请求
curl -X POST http://localhost:5000/register \
  -d "username=admin&password=x&email=x&phone=x"

😱 攻击结果
返回: UNIQUE constraint failed: users.username
攻击者确认 "admin" 已注册

4. 修复方案

4.1 VULN-12：充值金额上限

if abs(amount_num) > 10000:
  return redirect(f"/profile?user_id={user_id}")  # 单笔不超过 ±10000

4.2 VULN-13：防止余额为负数

new_balance = current_balance + amount_num
if new_balance < 0:
  return redirect(f"/profile?user_id={user_id}")  # 余额不低于 0

4.3 VULN-14：充值需要登录

if "username" not in session:
  return redirect("/login")  # 未登录的充值请求全部拒绝

4.4 VULN-15：隐藏错误详情

# 修复前：暴露 SQLite 底层错误
return render_template("register.html", error=f"注册失败: {e}")

# 修复后：通用提示
return render_template("register.html", error="注册失败，用户名可能已被占用")

5. 修复前后对照

/recharge 路由完整对比

❌ 修复前
def recharge():
  # 无登录检查
  user_id = request.form.get("user_id")
  amount = request.form.get("amount", "0")
  UPDATE users SET balance = balance + ?
  # 无上限、无负数检查
✅ 修复后
def recharge():
  if "username" not in session: redirect
  user_id = request.form.get("user_id")
  amount = request.form.get("amount", "0")
  if abs(amount) > 10000: redirect
  if new_balance < 0: redirect
  UPDATE users SET balance = ?
  # 三层防护：登录 + 上限 + 余额非负

本轮总结

业务逻辑漏洞是最容易被忽视的安全问题。代码没有语法错误，SQL 也没有注入风险， 但缺少业务规则校验导致用户可以做不合理的事。 修复的核心是 3 条规则：

  • 💰 金额控制：单次充值上限 ±10000，余额不能为负
  • 🔐 操作鉴权：修改余额必须登录
  • 🎯 信息最小化：错误提示不暴露数据库内部信息
